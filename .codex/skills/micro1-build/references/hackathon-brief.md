## What the page makes clear

- Every valid entry should present both a baseline solution and an improved solution.
- The improved solution should show meaningful improvement in capability, reliability, efficiency, coverage, or engineering quality.
- A submission is scored only after it passes eligibility, completeness, integrity, trace, and reproducibility checks.
- The submission must make the work easy to run, verify, and explain.

## Scoring rubric

Scored out of 100:

- `15` - Problem fit / user value
- `30` - Agent solution and engineering
- `20` - End-to-end quality
- `15` - Measured improvement
- `15` - Reproducibility
- `5` - Hot take / insights

## Tie-break order

- Higher Agent Solution and Engineering score
- Higher Reproducibility score
- Higher Measured Improvement score
- Higher End-to-End Quality score
- Final panel review of documented evidence

## Required submission package

- Complete solution code and improvement changelog
- Reproduction guide
- Solution video up to 5 minutes
- Agent trajectories

## Submission expectations implied by the page

- Optimize for demonstrable engineering judgment, not novelty alone.
- Prefer problems with a visible user bottleneck and a clean before/after comparison.
- Build the evaluation path early. If improvement cannot be measured, it will be difficult to score well.
- Preserve evidence continuously. Do not reconstruct the changelog or trajectories at the end.
- Reproducibility is part of the score and also part of the qualification gate.

## Practical operating guidance

- Start by extracting the exact acceptance criteria and hidden constraints from the released prompt.
- Define the baseline before implementing the advanced path.
- Decide what metrics or checks will prove improvement.
- Keep the stack boring and easy to reproduce unless the prompt forces otherwise.
- Record exact commands, data requirements, outputs, runtime, and cost as the build progresses.
